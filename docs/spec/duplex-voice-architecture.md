# 双工语音 Agent 架构：从串行回路到事件图

范围：Marcus 一轮对话从"用户开口"到"Agent 说完、事情做完"的全过程，以及让这个过程流畅所需的新节点、新角色和决策模型（Jev）的分工。
关联文档：`docs/jev-decision-layer.md`（决策层现状）、`docs/research/harness2-and-graph-engineering.md`（图工程调研）、`docs/spec/voice-ux-optimization-plan.md`（界面方案）。

---

## 0. 结论

1. **语音 harness 的核心约束是时间，不是文本。** 文字 Agent 的用户在屏幕前被动等待，沉默不要钱，输出能先看后用。语音 Agent 的沉默超过一秒就被当成故障，说出口的话不能撤回，用户随时会插话。这些压力文字 harness 都不用面对，所以把文字 harness 套上 ASR 和 TTS 不会得到好的语音体验。
2. **Marcus 现在本质上是"可打断的半双工串行回路"。** 一句话说完才开始处理；同一时间只有一个任务，新请求排队；干活的会话就是说话的会话；任何人声都会直接掐断 Agent 的发言。
3. **目标是"对话与执行解耦的事件图"。** 对话这条轨道永远在线，执行任务在旁边的轨道上跑；单一的音频输出通道由一个仲裁节点按"话权"分配；每个节点有自己的时间预算。
4. **决策模型（Jev）放在"判断层"。** 凡是答案空间事先已知、输入不依赖 LLM 输出的判断——用户说完没有、这个插话是什么意思、需不需要先应一声、这句话和正在跑的任务是什么关系、现在该不该开口——都交给 Jev，规则兜底。LLM 只负责生成内容和调用工具。
5. **新增角色以代码和 Jev 为主，不增加 LLM 调用。** 本文提出 7 个角色（第 5 节），其中"计时官"（Ticker）和"话权仲裁"（Floor Manager）是体验提升最大的两个；配套的"免费数据分析器"从已有的事件日志里统计工具耗时、用户耐心等，不需要任何模型。

## 1. 语音 harness 面对、而文字 harness 不面对的压力

| 压力 | 文字 Agent | 语音 Agent |
|---|---|---|
| 沉默 | 用户看着加载动画等，几十秒也能接受 | 约 1 秒没回应用户就会怀疑"它听见没"；3 秒以上会重复或放弃 |
| 输出不可撤回 | 生成完、校验完再展示 | 一开口就无法收回，念错的数字、编造的结论直接进入用户耳朵 |
| 重叠说话 | 不存在，输入框是独占的 | 用户会插话、附和（"嗯""对"）、自言自语，也会被环境噪声误触发 |
| 回合边界 | 用户按发送键，边界明确 | 只能从停顿和语义猜"说完了没有"；猜早了抢话，猜晚了显得迟钝 |
| 工具静默期 | 工具调用期间界面可以显示步骤 | 工具期间没有画面，只有沉默或"稍等" |
| 长时等待 | 用户可以去做别的事，回来再看 | 用户被"挂在电话上"；没有进度就只能干等 |
| 信息密度 | 可以给表格、链接、长列表 | 只能线性地听，30 秒以上的回答几乎记不住 |
| 并发诉求 | 开新对话窗口 | 用户在等一件事时顺口问另一件事，期待马上得到回答 |

所以，语音 harness 除了"把事做对"，还要持续回答用户心里的三个问题：**它听到了吗？它在干什么？我现在能说话吗？**

## 2. 现状诊断

### 2.1 一轮对话现在怎么走

```
用户说话 ─VAD─► STT ─► 语义缓冲（标点 + 0.5 s 定时）─► 最终转写
   ─► 规则路由 ─► Jev 判断（意图 / 角色 / 待确认回答，≈0.3 s）
   ─► 有任务在跑？── 是 ──► 排队，等当前任务结束（drainQueue 只用规则，不问 Jev）
            └ 否 ──► 创建任务 ─► 唯一的 activeTask ─► 角色会话（LLM + 工具）
   ─► Herald 过滤 ─► 语音队列（按优先级）─► 预合成 TTS ─► 播放

静默期填充：700 ms 收到确认（模板）；工具调用开始时一句"我来"；工具超过 5 s 后每 10 s 轮换 4 句固定话术。
打断：Agent 说话时检测到任何人声 → 立即取消播放并清空待播语音。
```

依据：`agent-runtime/src/tasks/task-executor.ts`（单一 `activeTask`、`pendingQueue`、`drainQueue` 只调 `reflexRouter`）、`agent-runtime/src/voice/*.ts`（确认语模板、填充话术）、`app/realtime/voice_activity.py` 与 `app/realtime/pre_synth_queue.py`（一检测到用户开口就打断）。

### 2.2 本次实测暴露的问题（2026-11-09，真实链路）

来自 P0 实施时用 `scripts/voice-smoke.py` 跑真实后端、TS 大脑和 LLM 录下的事件序列：

1. **多余的确认语。** 用户说"你好"，0.8 秒后 Agent 先说"嗯，我先看看"，0.4 秒后才说正式回复。闲聊根本不需要"我先看看"。
2. **误导性的确认语。** 用户说"请用一句话介绍你自己"，确认语是"我查一下"——实际上不会去查任何东西。
3. **抢话。** 自动模式下，合成语音中间的一个停顿被切成两轮；Agent 在用户还在说第二半句时（用户 2.89 s 才停）就从 2.67 s 开始回答第一半句。
4. **附和会掐断回答。** 代码层面，Agent 说话时任何被 VAD 识别为人声的声音都会触发打断，包括"嗯""对"这类附和，也包括咳嗽。
5. **等待时插话会被排队。** 一个搜索任务在跑时，用户问"现在几点"，这句话会进入队列，等搜索结束才处理。
6. **识别失败无声无息。** 识别服务欠费返回 429 时，用户这边只是"没反应"，没有任何口头或界面提示。

### 2.3 根因

这些现象不是单个 bug，而是同一个结构问题的不同侧面：

- **串行**：每个阶段等上一个阶段彻底完成。没有"边听边准备"，也没有"边干活边聊天"。
- **身份合一**：同一个 LLM 会话既是"在场的人"又是"干活的工人"。工人埋头干活时，就没有人陪用户说话。
- **时间无主**：沉默由几个互不知情的定时器各自管理，它们不知道正在发生什么、还要多久、用户有多着急。
- **打断无语义**：系统只知道"有人声"，不知道这个声音是什么意思，于是只能一律停下。

## 3. 重新理解"双工"

"全双工"常被理解为"能被打断"。这只是起点。按能力分五级：

| 级别 | 含义 | Marcus 现状 |
|---|---|---|
| L0 轮流说 | 对讲机式，一方说完另一方才能说 | 手动模式 |
| L1 可打断 | 用户开口，Agent 立即闭嘴 | 自动模式（已修复，可用） |
| L2 打断有语义 | 区分附和、叫停、纠正、补充、换话题、噪声，分别处理 | 只在**整句识别结束后**区分叫停 / 取消 / 纠正 / 追加；**说话当下**一律当叫停 |
| L3 对话与执行解耦 | 干活的同时还能聊天、回答状态询问、接新请求 | 不支持：单任务 + 排队 |
| L4 预测 | 用户还没说完就开始准备（预热角色、预取搜索），说完立刻回应 | 不支持（只有 Jev 期间的推测性预热在路线图里） |

**目标：完整的 L2 和 L3，加上 L4 中低风险的部分。** L2 和 L3 决定"像不像在和人说话"，L4 决定"快不快"。

还要分清两种"同时"：

- **信道上的同时**：用户和 Agent 同时出声。处理它的是媒体层和话权仲裁，时间尺度是百毫秒。
- **工作上的同时**：Agent 在说话 / 听话的同时在执行任务。处理它的是轨道调度，时间尺度是秒到分钟。

现在的设计把两者混在一起：一个声音事件既会停止播放，也会取消待播的工作成果。

## 4. 目标架构

### 4.1 四个时间层

每个节点归属一个时间层，层决定它能用什么"大脑"：

| 层 | 时间预算 | 谁来做 | 例子 |
|---|---|---|---|
| 反射层 | ≤100 ms | 代码，本地 | VAD、降低播放音量（ducking）、明确的"停"关键词、播放队列操作 |
| 判断层 | ≈300–500 ms | Jev，规则兜底 | 说完没有、插话是什么意思、要不要先应一声、路由、和当前任务的关系 |
| 思考层 | 1 s 以上 | LLM + 工具 | 生成回答、搜索、写邮件、写代码 |
| 沉淀层 | 分钟级，不在关键路径 | LLM / Jev / 代码 | Scribe 话题账本、记忆整理、决策分歧回流、离线评审 |

**规则：上层不能阻塞下层。** 思考层再慢，反射层和判断层也要照常运转；判断层超时，反射层的默认行为（规则）立刻接管。

### 4.2 两类轨道

```
                    ┌─────────────────────── 对话轨道（永远在线） ───────────────────────┐
麦克风 ─► 媒体层 ──►│ 回合判定 ─► 插话分类 ─► 意图/关系判定 ─► 主持人（短答/状态/确认）     │
                    └──────────────┬────────────────────────────────▲──────────────────┘
                                   │ 新任务 / 纠正 / 追加 / 取消       │ 进度、结果、需要确认
                    ┌──────────────▼──────────── 执行轨道（可多条） ───┴──────────────────┐
                    │ 任务 A：角色会话（LLM + 工具）─► 交付门                                │
                    │ 任务 B：……                                                          │
                    └──────────────────────────────────────────────────────────────────────┘
                                   │ 所有"想说的话"都是候选发言
                                   ▼
                    ┌────────────── 话权仲裁（唯一的输出通道） ──────────────┐
                    │ 计时官提供沉默预算和截止时间 │ 按优先级 / 新鲜度 / 时机挑一句 │──► TTS ─► 扬声器
                    └─────────────────────────────────────────────────────────┘
```

- **对话轨道**只有一条，它的职责是"在场"：听、判断、应答。它可以直接回答不需要工具的话（问候、状态询问、确认），但不会去执行重任务。
- **执行轨道**可以有多条。每条是一个任务，内部是 LLM 的工具回路（loop 住在节点里）。
- **所有想说的话**（确认语、进度、最终结果、授权询问）都先变成"候选发言"，由话权仲裁决定谁、何时、说不说。现在的语音优先级队列是它的雏形。

### 4.3 用图工程的四类节点对照

图工程笔记把节点分为拆分器、工人、代码节点、闸门四类（X-Notebook《Loops and Graphs》）。在语音场景里：

| 节点类型 | Marcus 中的对应 | 用什么实现 |
|---|---|---|
| 拆分器（splitter） | 意图 / 关系判定：这句话是新任务、纠正、追加、取消、状态询问，还是闲聊 | Jev |
| 工人（worker） | 角色会话（general、web、mail…）、主持人的短答 | LLM |
| 代码节点 | 播放队列、计时、ETA 统计、事件序号、文本规整 | 代码 |
| 闸门（gate） | 交付门（能不能念）、授权确认（按影响范围开闸）、话权仲裁 | 代码 + Jev；高风险动作由人确认 |

两条回路（同一笔记的"两条返回路径"）：

- **纠正边（短）**：交付门拒绝一段回答（太长、念不出、含未核实措辞）→ 退回工人重写成可念版本，只修本次。
- **学习边（长）**：Jev 和规则的分歧、用户的纠正与打断、超时记录 → 沉淀成约束（判断问题的措辞、阈值、角色提示词），修以后的每一次。现在这条边完全缺失。

**语音场景的额外规则：每条回路都有截止时间。** 文字 Agent 的回路可以"反复改直到通过"；语音 Agent 的回路必须在计时官给的时限内交付——到点还没通过，就交付一个降级版本（"我先说结论，细节稍后补"），而不是继续沉默。

## 5. 新增与强化的角色

下表的"大脑"一列：**代码**表示纯确定性逻辑；**Jev** 表示类型化判断、规则兜底；**LLM** 表示生成。

| 角色 | 职责 | 大脑 | 状态 |
|---|---|---|---|
| ① 计时官 Ticker | 掌管所有时间：沉默预算、任务 ETA、截止时间、什么时候该开口 | 代码 + Jev | 新增 |
| ② 话权仲裁 Floor Manager | 唯一输出通道的主人：挑选、合并、丢弃候选发言；处理插话时的降音 | 代码 + Jev | 由语音队列升级 |
| ③ 回合判定 Turn Judge | 判断用户是否说完 | Jev | 新增（替换标点 + 0.5 s 定时） |
| ④ 插话分类 Overlap Classifier | Agent 说话时用户出声：附和、叫停、纠正、补充、换话题、噪声 | 代码（降音）+ Jev | 新增 |
| ⑤ 应答门 Ack Gate | 要不要先应一声、应哪一类 | Jev | 替换固定 700 ms 模板 |
| ⑥ 主持人 Host | 执行轨道忙时陪用户说话：状态询问、闲聊、确认 | 代码模板 + Jev；必要时轻量 LLM | 新增 |
| ⑦ 进度叙述者 Progress Narrator | 把工具事件翻译成可念的真实进度 | 代码模板 + Jev 选择 | 替换 4 句固定话术 |

### ① 计时官（Ticker）

现在的沉默管理分散在三处定时器里，互不知情。计时官把"时间"变成一个有主人的资源。

**它维护的状态**（全部来自事件，不依赖 LLM 输出）：

- 当前阶段已持续多久：用户停顿、等待首句、工具运行、Agent 说话；
- 当前工具的预计耗时：由"工具耗时分析器"（第 6 节）给出 p50 / p90；
- 距离上一次 Agent 出声已过去多久；
- 本轮已经说了几次"过渡话"（防止啰嗦）。

**它做的事：**

1. 每 250 ms 跑一次纯代码判断（不调用模型）：沉默是否超过当前阶段的预算。预算按阶段区分，例如：
   - 用户说完到首次出声：1.2 s；
   - 工具运行中：首次 3 s，之后按 ETA 动态调整（超过 p50 时说一次进度，超过 p90 时说明"比平时慢"）；
   - Agent 说完后等待用户：不催促（沉默是用户的权利）。
2. 预算将要超时时，产出一个"需要发言"信号，交给话权仲裁和进度叙述者，而不是自己决定说什么。
3. 给执行轨道的回路下发截止时间（"8 秒内给出可念的结果，否则先交付部分结论"）。
4. 驱动界面的"思考中 / 仍在处理 / 比平时久"文案（与 UI 方案的状态机共用同一时间源）。

**何时用 Jev**：只在"需要发言"信号触发时问一次，问题例如"现在开口合适吗"（用户是否刚开始说话、上一句是否刚说完）——输入全是状态，无需 LLM 输出。

### ② 话权仲裁（Floor Manager）

**原则：任何时刻只有一个声音，而且应该是最有价值的那个。**

- 收集所有候选发言：确认语、进度、最终结果、授权询问、主持人的短答。每个候选带上来源任务、类型、产生时间和过期时间。
- 选择规则（代码）：授权询问 > 最终结果 > 用户直接询问的回答 > 进度 > 确认语。过期的丢弃（结果已经出来，就不再念"还在查"）；同一任务的多条进度只念最新的。
- 用户开口时（反射层，≤100 ms）：**先把播放音量降到约 30%，不立即停止**；把决定权交给插话分类。分类结果为叫停 / 纠正 / 换话题时再真正停止；为附和或噪声时恢复音量继续说。
- 多个任务的结果同时到达时，按用户提问顺序交付，并在第二个结果前加衔接语（"另外，刚才问的天气……"）。

### ③ 回合判定（Turn Judge）

替换语义缓冲里"标点 + 0.5 秒定时"的启发式（`docs/jev-decision-layer.md` 路线图第 1 项）。

- 触发：VAD 检测到停顿，且停顿超过约 200 ms。
- 输入：当前识别中间结果、停顿时长、本轮已说时长、上一轮 Agent 问了什么（如果有）。全部来自媒体层和对话状态。
- 问题："用户这句话说完了吗？"（完整 / 明显未完 / 不确定）。
- 处理：完整 → 立即结束回合；明显未完 → 继续等待，最长再等 1.5 s；不确定 → 走原来的定时规则。
- 收益：同时降低延迟（说完的句子不用等满 0.5 s）和抢话（"帮我查一下……"后的停顿不会被切开）。2.2 节第 3 条就是它要解决的问题。

### ④ 插话分类（Overlap Classifier）

Agent 说话时用户出声，现在一律打断。改为两步：

1. **反射层（0 ms）**：话权仲裁降音，暂停播放下一句，但不清空队列。
2. **判断层（≈400 ms 内）**：拿到用户这段话的识别中间结果后，问 Jev："这是附和、叫停、纠正、补充、换话题，还是与对话无关的声音？"
   - 附和 / 无关 → 恢复音量，接着说；
   - 叫停 → 停止播放，保留任务；
   - 纠正 / 补充 → 停止播放，把内容交给对应任务（steer / follow-up）；
   - 换话题 → 停止播放，按新请求处理。
3. 400 ms 内没有可用的识别文本（用户只发出了一个短音）→ 按停顿长度判断：短于 300 ms 视为附和，长于则视为叫停。

明确的"停""别说了"仍由规则即时执行，不等 Jev（现有原则保留）。

### ⑤ 应答门（Ack Gate）

替换"700 ms 内没有回复就说一句模板确认语"。用户说完时，与路由判断**放在同一次 Jev 调用里**多问一题："这句话需要多久才能回答？"

| 判断 | 行为 |
|---|---|
| 可以立即回答（问候、闲聊、常识） | 不说确认语，直接等回答（解决 2.2 节第 1 条） |
| 需要查一下（单次搜索、查邮件） | 说一句与动作相符的确认（"我查一下明天上海的天气"） |
| 需要较长时间（调研、多步任务） | 说明预期（"这个要花点时间，我做好告诉你"），并允许用户继续聊别的 |
| 不确定 | 回到现在的 700 ms 规则 |

确认语的措辞仍由代码模板生成（不调 LLM），但动词来自路由结果（搜索 / 邮件 / 设备），不会再对"介绍你自己"说"我查一下"。

### ⑥ 主持人（Host）

执行轨道忙时，对话轨道上需要一个能说话的角色。它的能力被刻意限制：

- **状态询问**（"好了吗""还要多久""你在干嘛"）：完全由代码根据任务状态和计时官的 ETA 回答，不调用 LLM，也不打断任务。
- **确认与授权**：替任务向用户提问、收集回答（与现在的确认机制合并）。
- **闲聊与简单问答**：用模板或一个极小的 LLM 调用回答（例如"现在几点"、"你好"）；凡是需要工具的请求一律转成新任务。
- **新请求**：交给"关系判定"（下一节的决策 D5）决定是并行、排队、替换还是合并。

这样，第 2.2 节第 5 条的场景变为：搜索在执行轨道继续，主持人立即回答"现在三点十分"。

### ⑦ 进度叙述者（Progress Narrator）

替换"还在查，快了""我再确认一下"这类与实际状态无关的固定话术。

- 数据来源：工具事件（开始、进度、结束、结果大小、来源数）。这些是工具的输出，**不是 LLM 的输出**，属于"免费输入"。
- 代码模板把事件翻译成句子："找到 5 个来源，正在比对""邮件草稿写好了，等你确认"。
- 只在计时官发出"需要发言"信号时，才问 Jev 一个问题："这条进度和上一次说的相比有没有新信息？"——没有就不说，宁可沉默也不重复。

## 6. 免费数据分析器

"免费"指输入不依赖 LLM 的输出：只来自事件日志、媒体层信号、工具返回的元数据和时钟。它们大多是**代码节点**，不需要任何模型，输出作为 Jev 判断的状态或计时官的参数。

数据源：SQLite `events` 表（已保留最近 20 万条事件，含每次工具调用的名称、耗时、结果大小，以及 `decision.made`）。

| 分析器 | 计算什么 | 谁使用 |
|---|---|---|
| 工具耗时分布 | 每个工具（及搜索的每个提供方）耗时的 p50 / p90，按小时滚动更新 | 计时官的 ETA；进度叙述者的"比平时慢" |
| 提供方健康度 | 最近 N 次调用的失败率、超时率（搜索已有冷却机制，可推广到 STT / TTS / LLM） | 话权仲裁决定是否提前告知"服务有点慢"；故障提示 |
| 用户耐心模型 | 历史上用户在沉默多少秒后会重复提问或打断 | 校准计时官的沉默预算（替代拍脑袋的 1.2 s / 3 s） |
| 打断画像 | 打断发生在回答的第几秒、之后是纠正还是换话题 | 调整回答长度上限、结论前置的力度 |
| 回合节奏 | 用户平均语速、句中停顿分布 | 回合判定的停顿阈值个性化 |
| 决策分歧 | Jev 与规则、Jev 与用户后续纠正的不一致 | 学习边：生成新的标注样本 |

这些分析器的结果每次都作为一个小的数字摘要放进 Jev 的状态里（例如"该工具通常 4 秒、最长 11 秒；已运行 7 秒"），让判断有依据，而不是让 Jev 自己去猜。

## 7. 决策清单：Jev、规则与 LLM 的分工

### 7.1 全部判断点

| # | 判断 | 现在 | 改为 | 输入是否"免费" | 预算 | 规则兜底 |
|---|---|---|---|---|---|---|
| D1 | 用户说完了吗 | 标点 + 0.5 s 定时 | Jev | 是 | 300 ms | 原定时规则 |
| D2 | 插话是什么意思 | 一律叫停 | 代码降音 + Jev | 是 | 400 ms | 按停顿长度 |
| D3 | 意图：新请求 / 叫停 / 取消 / 纠正 / 追加 | Jev（已上线） | 加入"状态询问""闲聊" | 是 | 并入 D6 | 关键词规则 |
| D4 | 交给哪个角色 | Jev（已上线） | 不变 | 是 | 并入 D6 | 关键词规则 |
| D5 | 与正在跑的任务的关系：独立 / 依赖 / 替换 / 合并 | 不存在（一律排队） | Jev | 是 | 并入 D6 | 排队 |
| D6 | 需要多久能答（应答门） | 700 ms 模板 | Jev | 是 | 与 D3–D5 同一次调用 | 700 ms 规则 |
| D7 | 是否在回答待确认的问题 | Jev（已上线，同意需 ≥0.9） | 不变 | 是 | 并入 D6 | 严格规则 |
| D8 | 现在开口合适吗 | 不存在 | Jev | 是 | 300 ms | 不开口 |
| D9 | 这条进度有新信息吗 | 不存在 | Jev | 是（工具事件） | 300 ms | 不说 |
| D10 | 搜索难度与时效性 | Jev（已上线） | 不变 | 是 | 450 ms | 规则 |
| D11 | Scribe 话题变了吗 | 每次扫描都调 LLM | Jev 先判断，变了才调 LLM | 是（转写文本） | 沉淀层 | 调 LLM |
| D12 | 回答能直接念吗（结论前置、长度、有无列表） | Herald 规则 | 规则 + Jev 评审 | **否**：输入是 LLM 输出 | 300 ms | Herald 规则 |
| D13 | 工具调用风险 | 未接入 | 单独评估 | **否** | — | 现有确认闸 |

D12、D13 依赖 LLM 的输出，不属于"免费"判断，按 `docs/jev-decision-layer.md` 的原则需要单独评估后再接入，本方案不把它们作为前提。

### 7.2 调用形状：每个时刻只调一次

实测表明，单次 Jev 调用在 1–64 个问题范围内延迟基本不变（约 320–410 ms），而**并行调用数**才是延迟悬崖（8 个并行 1.4 s，24 个 4.2 s）。所以设计上按"时刻"打包，而不是按"判断"拆分：

| 时刻 | 一次调用里的问题 |
|---|---|
| 用户停顿时 | D1 |
| 回合结束时 | D3、D4、D5、D6、D7（以及有搜索时的 D10） |
| Agent 说话中用户出声 | D2 |
| 计时官发出"需要发言"信号 | D8、D9 |

正常对话中，每一轮最多 2–3 次 Jev 调用，且彼此串行，不会撞上并行悬崖。连接预热和保活沿用现有实现（握手约 5 秒，必须保持热连接）。

### 7.3 上线纪律（沿用现有决策层的做法）

每个新判断都写成 `DecisionSpec`：阈值写在代码里，规则兜底，先 shadow 后 live，往 `eval/` 增加标注样本，`decision.made` 落库供审计。插话分类和回合判定的标注样本可以直接从 `voice-smoke.py` 的录音和真人对话的事件日志里提取。

## 8. 一轮对话的前后对比

场景：用户说"帮我查一下明天上海的天气"，搜索耗时 9 秒；搜索期间用户附和一声"嗯"，又问了一句"现在几点"。

**现在：**

```
0.0  用户开口
2.2  用户停顿 → 0.5 s 定时 → 结束回合
3.4  转写完成 → Jev 路由
3.7  700 ms 到 → "明天上海的天气啊，我看看。"
4.1  工具开始 → "我来。"
     用户："嗯" → 被当成打断，播放停止
9.1  工具已运行 5 s → "还在查，快了。"
     用户："现在几点" → 进入队列等待
13.2 搜索结束 → 念天气（约 8 秒）
21.0 队列中的"现在几点"才开始处理
```

**目标：**

```
0.0  用户开口
2.2  用户停顿 → D1 判定"完整"→ 结束回合（不等 0.5 s）
2.9  转写完成 → 一次 Jev 调用：新请求 / web 角色 / 需要查一下
3.2  确认语："我查一下明天上海的天气。"
     用户："嗯" → 降音 → D2 判定"附和"→ 恢复音量，不打断
     用户："现在几点" → D3 判定"闲聊"、D5 判定"独立"→ 主持人立即回答"三点十分"，搜索继续
8.0  计时官：已运行 4.8 s，该工具 p50 = 5 s → 进度叙述者："找到三个来源，正在核对。"
12.2 搜索结束 → 话权仲裁：结果优先 → "明天上海多云，最高 18 度，下午可能有小雨。"
```

关键差别：附和没有打断回答；等待中的提问被立刻回答；进度是真实状态；第一句回应提前约 0.5 秒。

## 10. 分阶段实施

每个阶段都能单独交付和验证；前一阶段的数据用于校准下一阶段。

| 阶段 | 内容 | 依赖 | 验收指标 |
|---|---|---|---|
| **S1 时间账与应答门** | `turn.trace` 节点耗时；工具耗时分析器；D6 应答门（shadow → live）；`drainQueue` 改走决策引擎 | 无 | 闲聊不再出现确认语；确认语动词与动作一致；每轮能看到各节点耗时 |
| **S2 计时官与进度叙述** | 计时官的沉默预算与 ETA；进度叙述者替换固定话术；主持人的状态询问（纯代码） | S1 的耗时数据 | 工具期间无超过 4 s 的沉默；进度话术零重复；"好了吗"在 1 s 内回答 |
| **S3 回合判定** | D1 shadow，用真人对话和录音校准后 live | S1 | 抢话率下降；平均"说完 → 首次出声"缩短 ≥0.3 s |
| **S4 插话语义** | 媒体层降音 / 暂停 / 恢复；D2 插话分类 | S3（共用部分识别文本处理） | 附和不再打断回答；叫停生效时间 <300 ms 不变 |
| **S5 对话与执行解耦** | 多轨道调度；D5 关系判定；话权仲裁；主持人闲聊 | S2、S4 | 任务运行期间的独立提问 2 s 内得到回答；多结果按提问顺序交付 |
| **S6 预测与学习边** | 部分识别结果高置信时预热角色、预取搜索；决策分歧回流成标注样本与约束 | S3、S5 | 首次出声 p50 再降；每周新增标注样本 |

**建议从 S1 开始。** 它改动小、风险低，并且为后续每个阶段提供校准数据。

## 11. 风险与边界

1. **Jev 不可用。** 握手需要约 5 秒，服务也可能中断。每个判断都有规则兜底，Jev 超时立即回落，反射层永远不依赖 Jev。
2. **"热心过度"。** 加了计时官和进度叙述者，Agent 可能变得话多。对策：计时官同时管"最少沉默"和"最多过渡话"；D9 没有新信息就不说。
3. **基于部分识别结果的判断噪声大。** D1、D2 用的是中间结果，准确率会低于整句判断。所以它们的错误代价设计得不对称：D2 判错"附和"只是多说半句，判错"叫停"会被用户再次打断纠正。
4. **多轨道带来的一致性问题。** 两个任务修改同一资源（例如两封邮件）时需要串行；D5 的"依赖 / 替换"选项就是为此存在，有疑问时退回排队。
5. **评测数据来源。** 现有 87 条标注是作者自标。插话、回合等新判断必须先在真人对话中以 shadow 模式收集数据再上线。
6. **授权闸不交给循环。** 发信、删除等高影响动作仍需用户口头确认，学习边只能提议修改判断的措辞和阈值，不能修改闸门本身（沿用 `harness2-and-graph-engineering.md` 的原则）。
7. **本地优先级。** 本方案不引入新的外部服务；除 D11（减少 LLM 调用）外，不增加 LLM 调用次数。
