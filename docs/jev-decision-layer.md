# Jev 决策层

Marcus 里有一大类决策，答案空间在提问之前就已知道，答案直接进一个 `if`：这句话交给哪个
专家？“好”是在回答待确认的问题吗？用户是想取消、纠正还是追加？它们不需要生成文字，
却过去要么靠手写关键词表，要么（在别的项目里）每次都付一次前沿 LLM 调用的价钱。

这一层把这类决策交给 **Jev**（TypeSafe 的 System One 模型）：输入一份状态和若干问题，
返回带概率的类型化答案（Choice / Score / Noul），不生成文字。规则始终在场作兜底。

背景与原则来自本机 X-Notebook 的 Jev 系列笔记（`AI/2026-09-2x-Jev-*.md`）：
生成归 LLM，执行归代码，**在已知选项之间做选择归 Jev**。

## 1. 它决定什么（以及不决定什么）

| 决策 | 谁决定 | 说明 |
|---|---|---|
| 明确的“停 / 取消 / 闭嘴” | **规则**，不问 Jev | 即时服从，不走网络，永远先于一切 |
| 这句话是新请求、停止说话、取消 / 纠正 / 追加正在跑的任务？ | Jev（规则兜底） | 选项随是否有任务在跑动态生成 |
| 新请求交给哪个专家 | Jev（规则兜底） | 选项 = 当前注册且有 `routingHint` 的角色 |
| 这句话是在回答待确认的问题吗（确认 / 拒绝 / 无关 / 不明）？ | Jev（严格规则兜底） | 只有 Jev 以 ≥0.9 的把握判定“同意”才算同意 |
| 工具调用是否危险、回复里有没有编造 | **未接入** | 这些依赖 LLM 的输出内容，不在“固定模式”范围内，见第 6 节 |

`code` 角色（带终端）和内部角色（scribe / inspector / memory）没有 `routingHint`，
**不会出现在语音路由的菜单里**——一句话不能直接触达带 bash 的角色。

## 2. 运行方式

```
transcript ──► ReflexRouter（规则，同步，<1ms）
                 │  明确的停止/取消 ──────────────────────────► 直接执行
                 ▼
              DecisionEngine
                 off     只用规则
                 shadow  规则决定；后台问 Jev，记录两者是否一致（不增加延迟）
                 live    连接已预热 → 问 Jev（预算 700ms）→ 置信 → 采用 Jev
                                              └ 超时/低置信/出错/未预热 → 采用规则
```

- 一次请求把所有适用的问题**并行**问完（intent、role、有待确认时再加 pending_answer），
  不是一问一答；问题之间互相看不到答案。
- 阈值都在 `src/decision/turn-decision.ts` 的 `TURN_THRESHOLDS`，在代码里、可评审：
  取消/停止说话 ≥0.85，纠正/追加 ≥0.75，新请求 ≥0.6，选角色 ≥0.6，**同意 ≥0.9**，拒绝 ≥0.6。
- 配置：`TYPESAFE_API_KEY`（没有就等于 `off`）、`AGENT_RUNTIME_JEV_MODE=off|shadow|live`
  （默认 `live`）、`JEV_MODEL`（默认 `jev-latest`）。启动日志打印 `[jev] mode=...`。

## 3. 连接：为什么要预热和保活

从这台机器到 `api.typesafe.ai` 的 **TLS 握手约 5.1 秒**，握手之后一次调用约 0.3 秒；
对比 DeepSeek / MiniMax / 智谱的握手只要 23–46 毫秒。所以客户端：

- 启动时在后台预热两条连接，未预热完成前所有决策直接用规则（不浪费预算、不触发熔断）；
- 每 15 秒 ping 一次，不让连接空闲到被服务端关掉；
- 每次调用有硬预算，超时即回落规则；连续 3 次失败熔断 30 秒。

**调用的形状**（2026-10-25 本机实测，热连接，每格 5 次取中位数）：

| 状态长度 × 问题数 | 延迟 |
|---|---|
| 100–6000 字符 × 1–8 个 | 317–339 ms，几乎不变 |
| ~17k token × 1–8 个 | 409 ms |
| 500 字符 × 32 / 64 个问题 | 340 / 412 ms |
| 500 字符 × 1 个，**并行 8 / 24 个调用** | **1400 / 4224 ms** |

- 单次调用的延迟在这个范围内主要是网络往返；输入 token 随问题数只增加约每题 55，没有观察到状态被重复计算。
  状态约超过 17–45k token 时服务端返回 `max_tokens_exceeded`（HTTP 400）。更长输入、更长输出下是否变慢这里没有测。
- 真正的拐点是**并行调用数**：同一连接上并行越多越慢。所以同一个状态上的多个判断放进**一次**调用的多个问题里，
  而不是拆成多次并行调用；评测里给一个查询的 ~25 个候选打分就是一次调用 25 个问题（~1 秒）。

## 4. 评测

`agent-runtime/eval/turn-cases.json` 是 87 条带标注的中英文话语（含关键词规则会误判的难例，
如“后端开发需要学哪些东西”会被“后端”关键词误路由到设备角色）。用真实 Jev 评测：

```bash
cd agent-runtime && npm run build
TYPESAFE_API_KEY=... node scripts/eval-turn-decision.mjs --verbose
```

2026-10-25 结果：

| | 规则（旧） | Jev（置信时） | 组合（live） |
|---|---|---|---|
| 总体 | 52% | 97% | **99%** |
| 新请求选角色 | 54% | 98% | 98% |
| 取消 / 纠正 / 追加 / 停止说话 | 25–33% | 100% | 100% |
| 回答待确认问题 | 61% | 91% | 100% |

- **误把非“同意”当成同意：规则 0，Jev 0，组合 0。** 真实的“同意”被漏认：规则 3，Jev 0。
- Jev 对 3/87 条放弃判断、回落规则；剩下 1 条错的标注本身有歧义（“看看有没有快递通知”）。
- 热连接延迟 p50 ≈ 325 ms，p95 ≈ 480 ms；87 次调用花费约 $0.0025（$0.042/百万输入 token）。

**局限：** 这是作者自己标注的 87 条，不是真实流量；它说明方向和量级，不是上线后的准确率。
真实准确率要靠 shadow 日志校准（下一节）。厂商宣称的 200× 速度 / 400× 成本是上限，不是承诺。

## 5. 审计与校准

每个决策（无论哪种模式）都会写一条 `decision.made` 事件进 `events` 表：规则的答案、Jev 的答案、
实际采用的、来源（jev / rule / rule_fallback）、把握、延迟、回落原因。

```bash
scripts/query-hci-events.sh --decisions     # 一致率、回落原因、延迟、最近的分歧
```

调阈值的流程：切到 `shadow` 跑一阵 → 看 `--decisions` 里的分歧是 Jev 对还是规则对 →
把分歧样本加进 `eval/turn-cases.json` → 改问题 / 阈值 → 重跑评测 → 再上 `live`。
问题措辞和阈值改了就升 `turnDecisionSpec.version`，让日志可以对比。

## 6. 路线图（尚未做）

按价值排序，都属于“答案空间已知、不依赖 LLM 输出”的决策：

1. **回合结束判定**（Python 媒体面 `SemanticBufferProcessor`）：现在靠标点 + 0.5 秒定时器猜用户说完没有，
   “这句话说完了吗？”是一个典型的 Noul 问题，能同时降低延迟和误切。
2. **Scribe 话题漂移门**：现在每次 sweep 都调一次 LLM；先问 Jev“话题变了吗”，没变就跳过 LLM。
3. **长任务安抚话术 / 工具确认语的选择**（`voice/`）：现在是定时器 + 模板。
4. **任务复杂度 → 模型档位**：目前所有角色统一 `deepseek-flash`，若引入 pro 档，用 Score 选档。
5. **工具调用执行前的风险闸**（LangChain 的 AutoMode 思路）：这一项依赖 LLM 产生的参数，
   属于对 LLM 输出的判断，需要单独评估后再接。
6. **Jev 作评审员**：离线对 trace 打分，是[自改进循环](research/harness2-and-graph-engineering.md)的评测底座。

另一个可做的优化：现在路由决策串行地多花约 0.3 秒；可在 Jev 判断期间推测性地预热最可能的角色会话。
